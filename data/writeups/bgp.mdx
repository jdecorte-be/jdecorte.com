## Overview

**BADASS (BGP At Doors of Autonomous Systems is Simple)** is a three-part 42 project that took me from basic container networking to running the same BGP EVPN control plane that data centers at companies like Amazon, Google, and Microsoft run in production. I built the whole thing in GNS3, one layer at a time: first a Docker-based lab environment, then VXLAN tunnels between hosts, then a full EVPN fabric that discovers those tunnels automatically over BGP.

None of it is simplified for the sake of the lab. The FRRouting configuration, the route types, the troubleshooting commands — all of it maps directly onto production hardware from vendors like Cisco and Juniper. That was the point: build real intuition for how data center fabrics work, rather than memorize a lab script that falls apart the moment something doesn't match the happy path.

Each part builds on the one before it, so the complexity creeps in gradually instead of hitting all at once.

## Part 1 — GNS3 Configuration with Docker

Every networking project needs a reliable test environment. Part 1 sets one up using GNS3 and Docker.

GNS3 gives you a graphical network simulator. Docker gives you lightweight containers that can stand in for network devices, without the overhead of full virtual machines. Containers share the host's kernel instead of running a separate OS, so you can run complex topologies on modest hardware — something full VMs would struggle with — and Docker images are easy to version and share, which keeps the lab consistent across machines.

You'll build two Docker images in this part:

- **A host image** — a simple device for generating and receiving test traffic.
- **A router image** — a full virtual router running multiple routing daemons.

This split mirrors real networks, where edge devices and core routing infrastructure play different roles.

### Setting Up the Lab Environment

Start by installing GNS3 and Docker in your VM. GNS3 handles the topology and simulation; Docker handles the containers. Together, they let you drag containers into a topology and wire them up like physical hardware.

Getting this right matters: you'll need to configure Docker's networking mode, enable IP forwarding on the host, and adjust firewall rules so containers can talk to each other. These steps also teach you Linux networking fundamentals — skills that carry over to everything else in this project.

### Building the Host Container Image

The host image should be small but functional. Alpine Linux is a good base: minimal, security-focused, and the standard choice for containerized workloads.

Example Dockerfile:

```dockerfile
FROM alpine:latest

# Install essential networking tools
RUN apk add --no-cache \
    busybox-extras \
    iproute2 \
    iputils \
    net-tools \
    bind-tools \
    tcpdump

# Keep container running
CMD ["/bin/sh"]
```

Make sure the image includes these tools:

- **ping** — test reachability between hosts
- **ip** — configure interfaces and routing tables
- **ifconfig** — check interface status
- **traceroute** — trace the path and measure latency
- **tcpdump** — capture packets for deep analysis

You'll use these constantly to verify each configuration step. Later in the project, these host containers become your test endpoints for VXLAN and BGP EVPN traffic. Keeping them simple makes troubleshooting easier — if something breaks, you'll know it's the network infrastructure, not the host.

### Building the Router Container Image

The router image is the core of your lab. It needs a more complete distro and several routing daemons.

Use FRRouting (the modern successor to Quagga). FRR's `zebra` daemon manages the kernel routing table and coordinates between protocols.

Example Dockerfile:

```dockerfile
FROM alpine:latest

# Install FRRouting (successor to Quagga)
RUN apk add --no-cache \
    frr \
    frr-pythontools \
    iproute2 \
    busybox-extras

# Enable IP forwarding
RUN echo "net.ipv4.ip_forward = 1" >> /etc/sysctl.conf && \
    echo "net.ipv6.conf.all.forwarding = 1" >> /etc/sysctl.conf

# Copy FRR daemon configuration
COPY daemons /etc/frr/daemons

# Expose BGP port
EXPOSE 179

CMD ["/usr/lib/frr/frrinit.sh", "start"]
```

Include these daemons:

- **zebra** — talks to the kernel routing table
- **bgpd** — handles BGP, including EVPN
- **ospfd** — OSPF, a link-state routing protocol
- **isisd** — IS-IS, another link-state protocol

This project focuses on BGP, but having other protocols available lets you compare approaches later. Each daemon runs separately and talks to zebra to install or remove routes. The configuration style mirrors real hardware from Cisco and Juniper — that's deliberate, since the skills transfer directly to physical routers.

### Verifying Connectivity

Once your images are built and imported into GNS3, wire up a simple topology and test it. This step matters: everything else builds on it.

```bash
# On Host1 (10.1.1.2/24)
ip addr add 10.1.1.2/24 dev eth0
ip link set eth0 up
ip route add default via 10.1.1.1

# On Router (10.1.1.1/24 and 10.2.2.1/24)
ip addr add 10.1.1.1/24 dev eth0
ip addr add 10.2.2.1/24 dev eth1
ip link set eth0 up
ip link set eth1 up

# On Host2 (10.2.2.2/24)
ip addr add 10.2.2.2/24 dev eth0
ip link set eth0 up
ip route add default via 10.2.2.1

# Test connectivity from Host1 to Host2
ping 10.2.2.2
```

A simple test topology: two hosts, each on a different subnet, connected through one router. This also gets you comfortable with GNS3's console access and basic interface configuration — skills you'll lean on repeatedly as the project grows.

<Callout type="tip">
If your router and host templates in GNS3 don't run with the `NET_ADMIN` capability (or `--privileged`), come back to this later — creating VXLAN interfaces in Part 2 will fail silently otherwise, and it's an easy thing to lose an hour to.
</Callout>

## Part 2 — Discovering VXLAN

Part 2 introduces VXLAN, which extends Layer 2 networks across Layer 3 infrastructure. To understand why VXLAN exists, start with what it replaced: the traditional VLAN.

### Understanding Traditional VLANs

![VLAN Architecture](/static/images/portfolio/badass/vlan.avif)

A VLAN splits one physical network into multiple logical ones, with no extra switches or cabling required. VLANs work at Layer 2, tagging Ethernet frames with a 12-bit identifier defined by the 802.1Q standard [@ieee8021q]. Think of them as virtual rooms: devices in the same VLAN talk directly at Layer 2, devices in different VLANs can't — even on the same switch. Any traffic between VLANs has to pass through a router, which can apply security rules along the way.

802.1Q adds a 4-byte tag to the Ethernet header, and its 12-bit ID field allows for 4096 VLANs, with a handful reserved — so about 4094 are usable in practice. That was enough for traditional enterprise networks. Cloud computing changed that.

### The Limitations of Traditional VLANs

Cloud-scale data centers exposed real cracks in the VLAN model:

- **Limited scale** — only 4096 available VLAN IDs
- **Geographic constraints** — can't span data centers without heavy engineering
- **Spanning Tree overhead** — blocks redundant links, wasting bandwidth
- **Manual provisioning** — needs configuration on every switch in the path
- **Multi-tenancy limits** — not enough isolation for cloud-scale environments

In multi-tenant clouds, each customer may need its own isolated network, which burns through VLAN IDs fast. VLANs are also stuck within a single broadcast domain — they can't naturally span multiple data centers. Spanning Tree Protocol makes this worse: STP blocks redundant links to prevent loops, so a chunk of network capacity sits idle. And adding a new VLAN often means touching every switch in the path by hand — slow, manual, and error-prone. None of this fits how modern, API-driven data centers operate. These limits are what drove VXLAN's design.

### VXLAN Architecture and Design

![VXLAN Overview](/static/images/portfolio/badass/p2.avif)

VXLAN takes a different approach [@rfc7348]. Instead of tagging frames, it wraps entire Ethernet frames inside Layer 3 UDP packets — sometimes called "MAC-in-UDP." This lets Layer 2 segments stretch across any IP network, including routed networks that span data centers or regions.

A VXLAN packet includes:

- **VXLAN Header** — 8 bytes of flags and the VNI
- **VNI (VXLAN Network Identifier)** — 24 bits, supporting 16 million networks
- **Outer UDP Header** — uses destination port 4789
- **Outer IP Header** — routes the packet through the underlay
- **Outer Ethernet Header** — frames it for the wire
- **Original Ethernet Frame** — the actual payload being tunneled

24 bits means 16 million possible network segments — a massive jump from 4096 VLANs, and more than enough for even the largest cloud deployments.

Example VXLAN interface setup:

```bash
# Create VXLAN interface on Linux
ip link add vxlan10 type vxlan \
    id 10 \
    dstport 4789 \
    local 10.0.0.1 \
    remote 10.0.0.2

# Bring up the interface
ip link set vxlan10 up

# Add to bridge
ip link add br0 type bridge
ip link set vxlan10 master br0
ip link set eth1 master br0
```

VXLAN uses UDP, not TCP. That avoids the overhead of connection setup and state tracking — the underlying IP network already handles routing, and if a packet gets dropped, TCP running *inside* the tunnel handles retransmission. VXLAN itself doesn't need to.

![VXLAN packet encapsulation, showing the outer Ethernet, IP, and UDP headers, the 8-byte VXLAN header carrying the 24-bit VNI, and the untouched original Ethernet frame as payload](/static/images/portfolio/badass/vxlan-packet.avif)

### VTEP: The VXLAN Tunnel Endpoint

![VTEP Architecture](/static/images/portfolio/badass/vtep.avif)

A VXLAN Tunnel Endpoint (VTEP) sits at the edge of each segment and handles encapsulation and decapsulation. It can live in a physical switch, a virtual switch on a hypervisor, or — as in this lab — a container network stack.

Here's what happens when a VTEP sends traffic to a remote segment:

1. It looks up which remote VTEP serves the destination MAC address.
2. It builds a VXLAN header with the right VNI.
3. It wraps the original frame in a UDP packet addressed to the remote VTEP.
4. It sends the packet into the underlay network.

The reverse happens on receipt: the VTEP strips the VXLAN header, reads the destination MAC, and forwards the original frame locally. Hosts never see any of this — to them, it looks like a normal Layer 2 network, no matter the physical topology underneath.

### The Performance Benefits of VXLAN

Traditional Layer 2 networks suffer from broadcast storms, where broadcast traffic hits every device on the network. VXLAN limits this by scoping broadcast traffic to only the VTEPs that have members in a given VNI — either through ingress replication, where the source VTEP sends a separate unicast copy to every other VTEP in the VNI, or through multicast in the underlay, where a single copy fans out at the routers. Ingress replication needs no multicast support from the underlay and is what most modern EVPN deployments use, at the cost of extra bandwidth at the source VTEP when a VNI has many members.

VXLAN also enables real multipath networking. Since VXLAN packets are just IP packets, they can be load-balanced across multiple links using standard ECMP. The UDP source port is derived from the inner frame's headers, so packets in the same flow take the same path — no reordering — while different flows can spread across multiple paths.

There's a design benefit too: the overlay and underlay are decoupled. You can optimize the underlay purely for throughput and latency, without worrying about what the overlay networks running on top of it need.

### Why VXLAN Wins Beyond Performance

Two more properties make VXLAN the default choice for multi-tenant data centers, beyond the raw scale numbers.

The first is isolation. Each VNI is sealed off from every other VNI at the VTEP — traffic can't cross between them unless you explicitly configure a path. That's what makes it safe for unrelated tenants to share the same physical switches: a compromised host in one VNI has no way into another. Any traffic that does need to cross VNIs has to pass through a Layer 3 device, which is exactly where you'd enforce firewall rules or run intrusion detection, and where security teams can apply different policies per VNI.

The second is cost. Building a separate physical network per tenant doesn't scale, in hardware or in operational overhead. VXLAN lets many virtual networks share the same physical infrastructure instead, and because segments are defined through APIs rather than touched switch-by-switch, provisioning gets faster and less error-prone. That same decoupling is what lets workloads move between data centers without a network reconfiguration.

## Part 3 — Discovering BGP with EVPN

Part 3 introduces BGP EVPN — the control plane that automates VXLAN at scale. Manually wiring up VXLAN tunnels between VTEPs works for a handful of devices, but it falls apart once you have dozens or hundreds. BGP EVPN solves this by letting VTEPs discover each other and build tunnels automatically.

### Understanding BGP Fundamentals

BGP has run the internet for decades [@rfc4271]. It exchanges routing information between the autonomous systems that make up the global network. As a path vector protocol, BGP tracks the full path to each destination — every AS traffic must cross — which lets it apply routing policy based on business relationships, performance, or other rules.

BGP's real strength is extensibility. It started out carrying only IPv4 routes. Multi-Protocol BGP extensions [@rfc4760] later added support for IPv6, multicast, VPNs, and — relevant here — EVPN routes, which carry Layer 2 and Layer 3 reachability for overlay networks.

BGP runs over TCP sessions between routers and sends incremental updates only when something changes, rather than re-sending the full routing table. That efficiency matters at scale — it's a big reason BGP is a solid foundation for overlay control planes.

### EVPN: Extending BGP for Ethernet VPNs

EVPN extends BGP [@rfc7432] to carry MAC address reachability alongside IP routes, which makes BGP the control plane for VXLAN overlays: it tells every VTEP which MAC addresses live behind which other VTEPs.

Here's the key shift: instead of learning MAC addresses through flooding (the traditional data-plane approach), EVPN learns them through BGP signaling. When a VTEP sees a new local MAC address, it advertises it to every other VTEP over BGP. Remote VTEPs install the forwarding state directly — no flooding required. This cuts broadcast, unknown-unicast, and multicast traffic dramatically.

EVPN also borrows route distinguishers and route targets from BGP VPN technology. Each VNI gets a route target, and VTEPs only import routes matching their configured targets, which keeps each VTEP's forwarding table lean — it only holds state for the VNIs it actually serves. The route distinguisher keeps identical MAC addresses in different VNIs from colliding in the BGP table.

### EVPN Route Types and Their Functions

EVPN defines several route types, each doing one job. This lab only exercises Types 2, 3, and 5 directly — Types 1 and 4 belong to a piece of the picture this two-VTEP topology doesn't need, but they're worth knowing exist, since production fabrics lean on them heavily.

#### Type 1 Routes — Ethernet Auto-Discovery

Type 1 routes matter once a device is multihomed to more than one VTEP — a common redundancy pattern in real fabrics. They serve two purposes: fast convergence, by letting a failed VTEP withdraw one route instead of every individual MAC it was advertising, and aliasing, which lets remote VTEPs load-balance traffic across all the VTEPs serving a multihomed segment.

#### Type 2 Routes — MAC/IP Advertisement

Type 2 is the core route type. It carries a host's MAC address, and optionally its IP address too.

What it does:
- Advertises MAC addresses learned locally
- Optionally includes the IP address, enabling ARP suppression
- Carries the VNI for multi-tenant separation
- Includes a MAC mobility extended community for VM migration

When a host ARPs for another host's MAC address, the local VTEP can answer directly from its EVPN-learned table — no need to flood the request across the network.

#### Type 3 Routes — Inclusive Multicast Ethernet Tag

Type 3 handles BUM traffic — broadcast, unknown unicast, and multicast. Every VTEP advertises a Type 3 route per VNI it belongs to, signaling it wants that VNI's BUM traffic.

What it does:
- Announces VTEP membership in a VNI
- Builds the flood list for BUM traffic
- Supports ingress replication or multicast-based flooding
- Needed for initial host discovery, before Type 2 routes exist

#### Type 4 Routes — Ethernet Segment

Type 4 routes are how multihomed VTEPs elect a Designated Forwarder for a given segment — the one VTEP responsible for forwarding that segment's BUM traffic. Without this election, every multihomed VTEP would flood the same broadcast frame, and hosts downstream would see duplicates.

#### Type 5 Routes — IP Prefix Routes

Type 5 enables routing between VNIs directly at the VTEP. While Type 2 carries individual host addresses, Type 5 carries whole IP subnets.

What it does:
- Advertises subnets, not single hosts
- Enables Layer 3 routing between VNIs
- Supports symmetric and asymmetric IRB (Integrated Routing and Bridging)
- Allows centralized or distributed gateway designs

The symmetric/asymmetric distinction is about where the routing lookup happens. Symmetric IRB routes twice — once at the ingress VTEP into a shared transit VNI, again at the egress VTEP into the destination VNI — so no VTEP needs to know about every VNI in the fabric, just the ones it directly serves. Asymmetric IRB skips the transit hop by doing both lookups on ingress, which is simpler to configure but requires every VTEP doing inter-VNI routing to carry every VNI it might route into, which scales worse.

### Building the BGP EVPN Control Plane

Start by configuring BGP sessions between every router acting as a VTEP. In large EVPN fabrics, route reflectors cut down on the number of sessions each router needs.

Example FRRouting BGP EVPN configuration:

```bash
# Configure BGP with EVPN on Router A (10.0.0.1)
router bgp 65000
  bgp router-id 10.0.0.1
  no bgp default ipv4-unicast
  neighbor 10.0.0.254 remote-as 65000
  neighbor 10.0.0.254 update-source lo
  
  ! Enable L2VPN EVPN address family
  address-family l2vpn evpn
    neighbor 10.0.0.254 activate
    advertise-all-vni
  exit-address-family
!

# Configure VXLAN interface with VNI 10
interface vxlan10
  vxlan id 10
  vxlan local-tunnelip 10.0.0.1
  bridge-access 10
!

# Associate VNI with BGP EVPN
router bgp 65000
  address-family l2vpn evpn
    vni 10
      rd 10.0.0.1:10
      route-target import 65000:10
      route-target export 65000:10
    exit-vni
  exit-address-family
!
```

You need two things running side by side: the standard IPv4 unicast address family for underlay reachability, and the EVPN address family for the overlay control plane.

Each VTEP needs its VNIs configured, along with a route distinguisher and route targets. The route distinguisher keeps BGP table entries unique. Route targets control which routes get imported where — this is how you'd implement policies like hub-and-spoke VNIs, where spokes can only reach each other through a central hub.

`advertise-all-vni` is the easy default for a lab: every locally configured VNI gets advertised automatically. Production fabrics often advertise VNIs more selectively instead, to keep control over exactly what each VTEP exposes.

### Dynamic VXLAN Tunnel Establishment

BGP EVPN builds VXLAN tunnels on demand. When a VTEP receives an EVPN route for a MAC address in one of its VNIs, it automatically creates the tunnel state needed to reach that VTEP — no manual neighbor configuration required, and the network adapts as VTEPs come and go.

This also saves resources. Rather than maintaining a full mesh of tunnels regardless of traffic, tunnels only form where there's actual demand, which at scale is a meaningful reduction in state each VTEP has to track.

When a host moves — through VM migration or container rescheduling — EVPN updates automatically. The old VTEP withdraws its route, the new VTEP advertises one, and every other VTEP updates its forwarding table. This is core to how modern data centers handle load balancing, maintenance, and failure recovery.

### Validation and Troubleshooting

Check your EVPN implementation at three layers:

**Underlay:**
- Confirm IP reachability between all VTEP loopback addresses
- Confirm the underlay routing protocol has converged (OSPF/ISIS/static)
- Test ECMP load distribution
- Measure baseline latency and packet loss

**Control plane:**
- Confirm BGP sessions are up between VTEPs
- Confirm the EVPN address family is active
- Check route target import/export config
- Validate Type 2, Type 3, and Type 5 route advertisements

**Data plane:**
- Test host-to-host connectivity across VTEPs
- Confirm VXLAN encapsulation with a packet capture
- Confirm MAC learning happens via the control plane, not flooding
- Validate ARP suppression

Useful commands:

```bash
# Check BGP neighbor status
show bgp summary
show bgp l2vpn evpn summary

# View EVPN routes
show bgp l2vpn evpn
show bgp l2vpn evpn route type 2
show bgp l2vpn evpn route type 3

# Check VNI status
show evpn vni
show evpn vni 10
show evpn vni 10 detail

# View MAC address table
show evpn mac vni 10
show evpn mac vni all

# Check VXLAN tunnel endpoints
show interface vxlan10
bridge fdb show

# Capture VXLAN traffic
tcpdump -i eth0 -n udp port 4789 -vv

# Verify underlay reachability
ping 10.0.0.2 -c 4
traceroute 10.0.0.2
```

Start at the underlay: if VTEP loopbacks can't reach each other, BGP sessions never come up, and nothing above that layer will work.

Next, check the control plane. Confirm BGP sessions are established and EVPN routes are flowing correctly — missing or malformed route advertisements are the most common source of EVPN problems, so get comfortable reading BGP's show output.

<Callout type="warning">
The most common reason an EVPN route never shows up on a remote VTEP isn't a broken BGP session — it's a route target mismatch. Double-check that the `route-target export` on one side actually matches the `route-target import` on the other. A typo here fails silently: no error, just a route that never arrives.
</Callout>

Finally, check the data plane. Generate traffic between test hosts and capture packets to confirm the right VNI is used, the right destination VTEP is targeted, and encapsulation/decapsulation both work as expected.

### Topology Implementation

A minimal EVPN fabric needs just two router VTEPs, each with a host attached in the same VNI. That's enough to show dynamic MAC learning, automatic tunnel setup, and cross-fabric communication.

Router A and Router B each run BGP with the EVPN address family enabled. They peer with each other — directly, or through a route reflector — and both are configured with the same VNI. As hosts talk, each router learns local MAC addresses and advertises them via Type 2 routes.

The VXLAN tunnel forms automatically once both routers exchange EVPN routes. From there, Router A encapsulates traffic from Host 1, and Router B decapsulates it before delivering it to Host 2. The reverse path works the same way. The hosts never know any of this is happening.

### Real-World Applications and Scaling Considerations

This isn't an academic exercise. Major cloud providers run VXLAN with BGP EVPN at massive scale — the same design you just built in GNS3 scales to data centers with tens of thousands of servers and millions of workloads.

Production deployments add a few more layers on top of what you built here:

- Route reflectors run in redundant pairs, to avoid a single point of failure in the control plane.
- VTEPs are often dual-homed to multiple underlay switches for data-plane redundancy — which is exactly where the Type 1 and Type 4 EVPN routes from earlier come into play.
- Traffic engineering — via ECMP or explicit prioritization — helps make sure critical workloads get the bandwidth they need instead of getting starved by everything else on the fabric.

## Key Takeaways

Three parts, but really one arc: basic container networking, then an overlay on top of it, then a control plane that automates the overlay. A few things stuck with me more than the rest:

1. **VXLAN's 24-bit VNI is the whole story.** 16 million segments instead of 4096 VLANs is what actually makes multi-tenant cloud networking possible at today's scale — everything else about VXLAN exists to serve that number.
2. **EVPN replaces flooding with signaling.** Learning MAC addresses through BGP instead of data-plane flooding is a small idea with a large effect: it's the difference between a fabric that scales to a few dozen switches and one that scales to thousands.
3. **Route targets are the real access control.** Import/export policy on route targets is what lets you build hub-and-spoke VNIs, shared services segments, or strict per-tenant isolation — all without touching the underlay.
4. **The underlay barely matters, and that's the point.** Once IP reachability exists between VTEP loopbacks, everything above it — VXLAN, BGP, EVPN — works the same whether the underlay runs OSPF, IS-IS, or static routes. That decoupling is what makes the design portable.
5. **Debugging beats reading.** Tracing a broken EVPN route through three layers — underlay reachability, BGP session state, then a packet capture on the wire — taught me more than any amount of documentation would have.

If you want to go further from here, anycast gateways and Kubernetes' own use of VXLAN for pod networking are the natural next steps — both build directly on what's in this lab.
